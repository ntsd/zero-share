# Subsystem: Encryption (WebCrypto)

Zero Share layers **optional application-layer file encryption** on top of WebRTC's DTLS. The motivation (per the README): DTLS secures the channel, but the unauthenticated SDP offer/answer link exchange is exposed to man-in-the-middle attack, so file content gets a second, independent encryption layer. All crypto uses the browser-native WebCrypto API (`crypto.subtle`) — no crypto dependencies are installed. [`repo://README.md#L30-L36`], [`repo://src/utils/crypto.ts#L1-L23`]

> **Factual state at HEAD:** the configuration is **RSA-OAEP with `modulusLength: 2048`, `hash: 'SHA-256'`** and **AES-GCM with `length: 256`**. (The 2026-10 commit that bumped the symmetric key changed AES 128→256; a follow-up commit raised the RSA modulus 1024→2048.) Both the RSA-OAEP encrypt and decrypt call sites pin `hash: rsaGenParams.hash` (SHA-256, the digest the key was generated with) in their WebCrypto option objects — omitting it silently falls back to the implementation default digest instead of the declared one (PR #73), and `tests/crypto.test.mjs` — one of the regression guards `npm test` runs via `node --no-warnings --test "tests/*.test.mjs"` — pins the 2048-bit modulus **and** the SHA-256 digest pin (static regex checks plus a runtime AES-key RSA-OAEP round-trip through the real module) so any future revert fails `npm test`. The README states the layer accurately: "End-to-end encryption: RSA-OAEP (2048) wraps a per-file AES-256-GCM key (WebCrypto)" and "a per-file AES-256-GCM key wrapped with RSA-OAEP-2048 (hybrid encryption via WebCrypto)" — PR #93 corrected the earlier informal "PGP" label, and there is no PGP anywhere in the stack. [`repo://src/utils/crypto.ts#L1-L11`], [`repo://src/utils/crypto.ts#L44-L77`], [`repo://tests/crypto.test.mjs`]

## Key management: one RSA pair per peer, one AES key per file

- Each peer generates **its own RSA-OAEP-2048 key pair** (`publicExponent 65537`, SHA-256 hash) when it creates its outgoing artifact — the offer peer **exactly once per `generateOfferLink()` invocation, at the top (before the peer is created)**, so the ICE-candidate-completion and 3 s timeout build paths can never race and re-mint a key that no longer matches the link's `p` param (which previously broke every encrypted transfer when both paths ran); the answer peer inside `generateAnswerSDP`, which first awaits the validated import of the `p`-param key so a malformed key downgrades the session to plaintext before any answer is advertised. The key pair is held in page-level state (`rsa` private + `rsaPub` imported). [`repo://src/utils/crypto.ts#L1-L17`], [`repo://src/components/OfferPage.svelte#L152-L165`], [`repo://src/components/ReceivePage.svelte#L180-L189`]
- The peers exchange **public keys through the shared artifacts**: the offer peer's base64 public key is embedded in the offer link's `p` query param, and the answer peer's base64 public key is appended after `|` in the answer code. The answer page _derives_ `isEncrypt` from the presence of `p`, so encryption mode propagates from the offer side automatically. [`repo://src/components/OfferPage.svelte#L75-L90`], [`repo://src/components/ReceivePage.svelte#L33-L49`], [`repo://src/components/OfferPage.svelte#L288-L311`]
- When the sender picks files, **each file gets a fresh AES-256-GCM key**; that key is exported raw and wrapped (`encrypt`) with the receiver's RSA public key — using the SHA-256-pinned RSA-OAEP options, so the padding digest matches the keygen params. The wrapped key bytes ride in the `MetaData.key` field of the first `metaData` message. The receiver unwraps it with its private key in `onMetaData` and keeps the resulting `CryptoKey` on the file detail. **Before** that unwrap, `onMetaData` sanitizes the peer-controlled `MetaData.name` via `sanitizeName` — one rule covering all sinks — so a path-traversal name can no longer reach the store-only ZIP writer or `<a download>` (full detail in file-transfer.md; PR #98). The entry is **registered in `receivingFiles` at `WaitingAccept` before the async key decryption** — so a key-unwrap failure surfaces as a visible error entry instead of the file silently never appearing: `onMetaData` catches the `decryptAesKeyWithRsaPrivateKey` rejection, sets `error` on the entry, toasts `<name> failed to decrypt the file key`, and **sends `EVENT_VALIDATE_ERROR` back to the sender** (the sender's only transitions are peer-driven, so without this signal its file would sit in `WaitingAccept` forever), then returns without accepting. The success path is equally careful: the entry is **deniable/removable during the decryption await** (the list UI shows Accept/Deny on `WaitingAccept` entries since PR #76; `onDeny` deletes the entry), so `onMetaData` re-reads `receivingFiles[id]` and null-guards it before assigning `aesKey` — a Deny that lands in that window makes the handler return quietly instead of throwing `Cannot set properties of undefined (setting 'aesKey')` as an unhandled rejection outside any try/catch (PR #101). The key-unwrap **catch** path is null-guarded the same way (PR #103): it re-reads `receivingFiles[id]` and bails when the entry was denied during the decryption await, so its `error` write can no longer throw an unhandled `TypeError` — the second unguarded post-await write in this handler, fixed after the success path (`tests/receiver-metadata-key-catch-null-guard.test.mjs` pins it statically and with a mocked decrypt that denies the entry mid-await). Pick-time crypto failures are equally visible: `onFilesPick` iterates with an `async` `for...of` (not a fire-and-forget `forEach(async ...)`, so rejections cannot escape unhandled) and a `generateAesKey()` / `encryptAesKeyWithRsaPublicKey()` failure toasts `Failed to encrypt the file key for <name>` and skips the entry instead of registering an undeliverable one (PR #75). A metadata-validation failure at pick time is treated the same way (PR #96): the shared `validateFileMetadata` run at pick time rejects `size <= 0` / non-finite (a 0-byte file), toasts the error, and `continue`s — the entry is **never registered** in `sendingFiles`, because such a file can never complete (the receiver bounces it with `EVENT_VALIDATE_ERROR` on every resend and `processChunk`'s exact-match gate can never be satisfied by an empty payload), so registering it as a Resend-able `Pending` entry was a guaranteed dead-end that re-fired a "Receiver validate error" toast on every retry. A metadata-failed entry (unwrap failure, missing `aesKey`) additionally **cannot be force-accepted**: `Receiver.onAccept` guards its entry point and refuses such entries with a toast plus `EVENT_RECEIVER_REJECT` instead of starting a transfer that can never succeed (PR #78). [`repo://src/components/sender/Sender.svelte#L330-L401`], [`repo://src/utils/crypto.ts#L44-L77`], [`repo://src/components/receiver/Receiver.svelte#L37-L114`], [`repo://src/components/receiver/Receiver.svelte#L384-L406`], [`repo://tests/receiver-key-decryption-failure.test.mjs`], [`repo://tests/receiver-metadata-key-catch-null-guard.test.mjs`], [`repo://tests/sender-onfilespick-crypto-rejection.test.mjs`], [`repo://tests/sender-onfilespick-invalid-size-rejection.test.mjs`]
- **A file picked before the peer answer is accepted is rejected, not registered with an empty key.** `rsaPub` only exists after `acceptAnswer` imports the peer's key from the answer code, but the drop zone is live as soon as the data channel opens — i.e. while the offer is still pending. `Sender.onFilesPick` therefore rejects the pick with an error toast ("<name> cannot be sent encrypted yet: the peer has not accepted the offer. Accept the answer, then select the file again.") when `isEncrypt` is on and `rsaPub` is still `undefined`, instead of silently registering the entry with an empty wrapped key that the receiver's `decryptAesKeyWithRsaPrivateKey` would reject and dead-end the whole encrypted transfer. Note that an offer regeneration also clears `rsaPub` (the new generation re-mints the sender's keypair), so the same guard covers picks made between generations. [`repo://src/components/sender/Sender.svelte#L336-L355`], [`repo://src/components/OfferPage.svelte#L192-L200`], [`repo://tests/sender-encrypt-before-accept.test.mjs`]

## Payload encryption: AES-256-GCM with prepended IV

- `encryptAesGcm` generates a **random 12-byte IV per chunk**, encrypts the chunk, and returns `IV || ciphertext` as a single buffer. `decryptAesGcm` splits the first 12 bytes as the IV and decrypts the remainder. Per-chunk IVs mean each chunk's nonce is unique. [`repo://src/utils/crypto.ts#L26-L41`], [`repo://src/utils/crypto.ts#L78-L93`]
- The sender encrypts each chunk before framing it as a `Message` with the file id; the receiver decrypts each chunk after decoding, on its per-file serialized chunk queue (inside `processChunk`), before accumulating bytes into the file blob — and the receiver sends the `EVENT_RECEIVED_CHUNK` ack **only after successful decryption** (and after re-checking that the file is still active), so a corrupt chunk never advances the sender past a chunk it cannot use. [`repo://src/components/sender/Sender.svelte#L173-L204`], [`repo://src/components/receiver/Receiver.svelte#L177-L261`]
- GCM provides authenticated encryption: a corrupted or tampered chunk fails `decrypt`, and `processChunk` routes that failure to `rejectCorruptChunk` instead of silently dropping it — the file is marked errored, its status bounces back to `Pending`, an error toast fires, and an `EVENT_RECEIVER_REJECT` is sent so the sender stops cleanly, instead of the byte count never catching up and the file sitting in `Processing` forever. [`repo://src/components/receiver/Receiver.svelte#L182-L195`], [`repo://src/components/receiver/Receiver.svelte#L263-L298`], [`repo://tests/receiver-chunk-failure.test.mjs`]

## Key serialization

- RSA public keys are exported/imported as **SPKI DER, base64-encoded** (`exportKey('spki')` → `arrayBufferToBase64`; `importKey('spki')` with `rsaGenParams`, usage `['encrypt']`) via the `exportRsaPublicKeyToBase64` / `importRsaPublicKeyFromBase64` wire helpers. The 12-byte AES raw key is base64-URL-encoded only when it must cross the wire as a string parameter — in practice it travels as raw bytes inside the proto `MetaData.key` bytes field after RSA wrapping. [`repo://src/utils/crypto.ts#L97-L138`]
- `arrayBufferToBase64` / `base64ToArrayBuffer` are the shared codec helpers for the SPKI export path; the base64 conversion is chunked in 32 KiB slices because `String.fromCharCode.apply(null, largeArray)` overflows the JS call stack beyond ~65k elements. `tests/crypto-base64-wire.test.mjs` (PR #72) pins the wire contract at runtime: base64 round-trips byte-identically (all three remainder cases, edge byte values, and a 1 MB buffer) and matches the platform reference charset, the RSA key survives export → base64 → import → re-export with the JWK modulus/exponent intact, and the imported public key can actually encrypt an AES key that the private key decrypts. [`repo://src/utils/crypto.ts#L97-L138`], [`repo://tests/crypto-base64-wire.test.mjs`]

## Opt-out and failure behavior

- **Encryption is off by default** (`DEFAULT_SEND_OPTIONS.isEncrypt: false`). When off, no RSA keys are generated, `MetaData.key` stays empty, and `sendBuffer` sends plaintext chunks — the code paths simply skip every crypto call. [`repo://src/configs.ts#L41-L45`], [`repo://src/components/sender/Sender.svelte#L173-L204`]
- Defensive fallbacks: `sendBuffer` sends a plaintext chunk if `isEncrypt` is true but the per-file `aesKey` is somehow missing; the receiver decrypts only when both `isEncrypt` and the file's `aesKey` are present. [`repo://src/components/sender/Sender.svelte#L173-L204`], [`repo://src/components/receiver/Receiver.svelte#L182-L195`]
- **Key-exchange validation is explicit, not fire-and-forget.** The receive page imports the `p`-param key with a `catch` that downgrades `isEncrypt` to `false`, toasts "Invalid encryption key in link, falling back to plaintext", and resolves `undefined` — so the session silently degrades instead of advertising encryption while sending nothing usable. The offer page wraps its answer-code key import in `try/catch`: a malformed or truncated answer code toasts "Invalid encryption key in answer code" and aborts before `setRemoteDescription`, instead of leaving a half-configured connection. **The empty-key case is different and valid:** when the answer code is well-formed (has the `|` separator) but its key portion is empty, the receiver deliberately downgraded to plaintext because its `p` key was malformed — the offer page now follows the receiver into plaintext (`effectiveEncrypt = false`, info toast) instead of bailing on the empty key and dead-ending the handshake. A pick that fails key encryption at pick time (`generateAesKey` / `encryptAesKeyWithRsaPublicKey` rejection) is likewise skipped with a visible error toast and never registered (PR #75), and a pick whose metadata fails validation at pick time (e.g. a 0-byte file: `size <= 0` / non-finite) is treated identically — toast, `continue`, no entry in `sendingFiles` (PR #96). [`repo://src/components/ReceivePage.svelte#L46-L59`], [`repo://src/components/OfferPage.svelte#L304-L346`], [`repo://tests/answer-key-plaintext-downgrade.test.mjs`], [`repo://tests/sender-onfilespick-crypto-rejection.test.mjs`]
- **Effective encryption is tracked, not read live.** The offer page keeps `effectiveEncrypt` as a plain `$state` (a live `$state`-from-`$state` initializer would silently go stale because the Settings panel stays open and mutable while the offer is active); the accepted answer's key portion settles it for the handshake (present → `true`, empty → `false`). `onOptionsUpdate` re-syncs it from the setting **only while no offer link exists** (and clears the imported `rsaPub` in that window) — once the link is live, the session's mode is pinned by the link's `p` key and a mid-session options change (chunk size, ICE server, or a synthetic encryption flip) must not wipe `rsaPub` or move `effectiveEncrypt`, or the next file would be sent with an empty key the receiver cannot decrypt, or Sender/Receiver would desync from the peer's settled mode. Regenerating the offer link re-pins `effectiveEncrypt` from the live setting and clears `rsaPub` as part of the dead-generation teardown (PR #68), so a new generation never encrypts with the previous peer's RSA key. The encryption select is also disabled once the link is live (`encryptionLocked`). [`repo://src/components/OfferPage.svelte#L31-L38`], [`repo://src/components/OfferPage.svelte#L363-L384`], [`repo://src/components/OfferPage.svelte#L153-L219`], [`repo://src/components/OfferOptions.svelte#L38-L58`]
- **Receiver key-unwrap failure is visible, not silent, and it signals the sender.** If `decryptAesKeyWithRsaPrivateKey` rejects for an incoming file (corrupt wrapped key, missing/undefined private key), the already-registered entry gets `error` set, an error toast fires, and `onMetaData` sends `EVENT_VALIDATE_ERROR` back over the channel before returning without accepting — the sender's file (whose only transitions are peer-driven) bounces to `Pending` instead of waiting indefinitely for an accept that will never come. The metadata-failed entry remains visible in the file list with its error, so in manual-accept mode it is not a Remove-only dead-end (PR #76) — but pressing **Accept** on it is refused (PR #78): `onAccept` checks the entry's `error`/`aesKey` state up front, toasts `Cannot accept <name>: the metadata/key failed to process — the sender must resend the file`, and sends `EVENT_RECEIVER_REJECT` instead of emitting `EVENT_RECEIVER_ACCEPT` (without a usable key the transfer can never succeed: an encrypted session would either assemble the raw ciphertext as a "Success" blob or hit `rejectCorruptChunk` on every chunk — an N-toast storm per resend); the entry stays in `WaitingAccept` so Deny/Remove remain the real exits. `tests/receiver-key-decryption-failure.test.mjs` pins this end-to-end, and `tests/receiver-metadata-key-catch-null-guard.test.mjs` (PR #103) additionally pins the catch path's own null guard: the error write re-reads `receivingFiles[id]` and returns quietly when the entry was denied during the decryption await, instead of throwing an unhandled `TypeError` on the `receivingFiles[id].error` assignment. [`repo://src/components/receiver/Receiver.svelte#L37-L114`], [`repo://src/components/receiver/Receiver.svelte#L384-L406`], [`repo://tests/receiver-key-decryption-failure.test.mjs`], [`repo://tests/receiver-metadata-key-catch-null-guard.test.mjs`]

## Threat model notes

- This layer protects **file content confidentiality and integrity against SDP-link interception** (passive MITM), not against an active attacker who can modify the shared link or answer code end-to-end (they could swap public keys).
- RSA-OAEP-2048 key wrapping provides the standard 2048-bit modulus (the same strength as widely deployed RSA), and the per-file AES-256-GCM payload security is bounded by that symmetric algorithm. [`repo://src/utils/crypto.ts#L1-L6`], [`repo://tests/crypto.test.mjs#L6-L21`]
