# Subsystem: File Transfer Engine

The transfer engine is the `Sender` and `Receiver` Svelte components plus the `src/proto/message` code generated from `src/proto/message.proto` (`npm run protogen` via `ts-proto`). It implements a small **receiver-acknowledged chunk protocol** over the WebRTC data channel.

## Message framing

Every data-channel message is a protobuf `Message`: a `file id` plus exactly one of three payloads — [`repo://src/proto/message.proto#L1-L31`]

- `metaData` (`MetaData {name, size, type, key}`) — announced by the sender before any bytes; `key` holds the RSA-wrapped per-file AES key (empty when encryption is off). `size` is `int64` on the wire (PR #42 / commit 721c502 widened it from `int32`), so files ≥ 2 GiB no longer throw `invalid int32` during `Message.encode`.
- `chunk` — one slice of file body (raw or encrypted).
- `receiveEvent` — receiver→sender control: `EVENT_RECEIVER_ACCEPT`, `EVENT_RECEIVER_REJECT`, `EVENT_RECEIVED_CHUNK`, `EVENT_VALIDATE_ERROR`.

**File ids are unique, not filenames.** The sender assigns each picked file `crypto.randomUUID()`, so two same-named files transferred in one session get distinct ids and never cross-wire chunks; display uses `metaData.name` only. [`repo://src/components/sender/Sender.svelte#L419-L441`]

**Pick-time metadata rejection (PR #96).** `onFilesPick` runs the shared `validateFileMetadata` on each file's metadata _before_ registering the entry: a failure (the only reachable pick-time case is `size <= 0` / non-finite — e.g. a 0-byte file) toasts the error and `continue`s, so the entry **never enters `sendingFiles`** at all. Registering it as a Resend-able `Pending` entry was a guaranteed dead-end: a 0-byte file can never complete (the receiver bounces it with `EVENT_VALIDATE_ERROR` on every resend, and `processChunk`'s exact-match gate `receivedSize === size` can never be satisfied by an empty payload), so every retry re-fired a "Receiver validate error" toast for an undeliverable file. [`repo://src/components/sender/Sender.svelte#L425-L439`], [`repo://tests/sender-onfilespick-invalid-size-rejection.test.mjs`]

**File pick & paste scoping.** Files enter the session via `DragAndDrop` (drop, file picker, or clipboard paste). Its document-level `paste` listener is scoped: it ignores events whose target is an `INPUT`, `TEXTAREA`, `SELECT`, or content-editable element — so pasting an answer code or a custom ICE server value into any text field on the page no longer silently adds a stray `clipboard.txt` to the sender file list (PR #52) — and the listener is removed in `onDestroy` so it never outlives the component. [`repo://src/components/sender/DragAndDrop.svelte#L98-L134`], [`repo://tests/drag-drop-paste.test.mjs`]

## Sender state machine

Files live in a reactive `sendingFiles` map keyed by id, each carrying the `File`, `MetaData`, progress/bitrate, a `stop` flag, an `error`, and the per-file `aesKey`. Lifecycle: `Pending → WaitingAccept → Processing → Success`, with `Processing → Pending` (reset) on receiver reject or validate error. The guarded channel send is the shared `createChannelSender(dataChannel)` helper from `src/utils/channelSender.ts` (PR #97 — deduplicated from the receiver's identical copy, mirroring the `peerMessage.ts` handler dedup): `send()` no-ops with `false` when the lost flag is set or `readyState !== 'open'`, returns `true` on success, and on a throwing send flips the lost flag and returns `false` instead of leaking `InvalidStateError`; `markLost()` is the idempotent flip fired by `onChannelClose()`; and the sender's `connectionLost` flag is a **`$state`** the template reacts to — **not** a `$derived` over `channelSender.isLost()` (which would cache `false` forever, since `isLost()` reads a plain closure variable), flipped by `onChannelClose()` and by the `send()` wrapper that mirrors the helper's lost flag (PR #109) — it marks that the data channel will never deliver again, so from then on every send no-ops and the in-flight pipelines exit quietly instead of surfacing misleading per-chunk errors. Call sites keep their plain `send(...)` shape through the wrapper (which also mirrors the helper's lost flag into the UI `$state`). [`repo://src/utils/channelSender.ts`], [`repo://src/components/sender/Sender.svelte#L22-L49`], [`repo://tests/channel-sender.test.mjs`]

Flow for `onSend(key)`:

1. Register an `EventEmitter` for this file and bind handlers for the four `receiveEvent`s (routed by `receiveEventToJSON`). The handlers re-read the **live** entry from `sendingFiles[key]` after each await and bail if it was removed; chunk-send failures from either the `ACCEPT` or the `RECEIVED_CHUNK` path funnel into the single shared `markChunkFailed` helper (deduplicated from two identical catch blocks, PR #70), so a chunk failure lands as a visible error entry (`Failed to send chunk: …`, status → `Pending`, toast) instead of an unhandled rejection from the async listener.
2. Send the `metaData` message through the guarded `send()` (which no-ops on a dead channel — a Resend after the peer disconnected used to throw `InvalidStateError` here and surface the misleading "Failed to encode file metadata" while the file looped in `Pending` forever; a genuine encode failure still records its own error and resets to `Pending`); status → `WaitingAccept` on success, and a dead channel surfaces the accurate "connection lost — transfer aborted" error instead.
3. On `ACCEPT`: status → `Processing`, start the chunk loop.
4. On each `RECEIVED_CHUNK` ack: a `stop` bails **only while bytes remain** (`offset < metaData.size` — a mid-file pause); a `stop` with `offset >= size` (Stop clicked during the final chunk's send/ack window) must still finish the entry, not reset it — otherwise the file stays stuck in `Processing` and a later `Continue` re-sends the last chunk, which the receiver's exact-size gate rejects as an overshoot on a fully delivered file. An entry already at `Success` is **terminal**: a stray or synthetic ack (e.g. one `onContinue` emits from a Continue button still rendered when the completion ack raced in) returns without bouncing it back to `Pending`. Not `Processing` (and not `Success`) resets to `Pending` with progress 0; if `offset < metaData.size`, send the next chunk; else status → `Success`, clear `stop` (so a finished entry never renders a `Continue` button), and toast. [`repo://src/components/sender/Sender.svelte#L132-L179`]
5. `REJECT` / `VALIDATE_ERROR`: set the error, toast, status → `Pending` (retryable via re-send).

**Removing an in-flight file is safe.** The chunk pipeline is driven by async continuations that can outlive a `Remove`: `onRemove` sets `stop` (if `Processing`) **before** deleting the entry, and the pipeline only dereferences the entry reference captured at `onSend` entry (never a live re-read of `sendingFiles[key]` after an await), re-checking `stop` and the live entry at every await boundary in `sendNextChunk`/`sendBuffer`. Previously a removed in-flight file leaked an uncaught `TypeError` when the pending continuation dereferenced `sendingFiles[key].aesKey`/`.progress` after `onRemove` had deleted the entry. [`repo://src/components/sender/Sender.svelte#L367-L374`], [`repo://src/components/sender/Sender.svelte#L335-L365`], [`repo://src/components/sender/Sender.svelte#L197-L291`], [`repo://tests/sender-remove-inflight.test.mjs`]

**Connection loss is accurate, not per-chunk.** `onChannelClose` (fired by the page's `dataChannel` `onclose`/`onerror`) calls the shared helper's `markLost()` (guarding on `isLost()` so it runs at most once) and marks every non-`Success` file with a single accurate "connection lost — transfer aborted" error (`Processing` files also get `stop = true` to stop in-flight continuations), instead of a dead channel throwing `InvalidStateError` into each chunk pipeline — which previously leaked misleading "Failed to send chunk: InvalidStateError…" / "corrupt chunk" toasts, unhandled rejections, and in-flight files stuck in `Processing` forever. `onContinue` refuses to re-enter the pipeline when `channelSender.isLost()`. The file-list UI reflects this: `SendingFileList` receives the owning `Sender`'s `connectionLost` flag (a `$state` the template reacts to, flipped by `onChannelClose()` and the `send()` wrapper — not a `$derived` over the helper's `isLost()`, which would cache `false` forever since that reads a plain closure variable, PR #109) as a prop, and when it is set it **suppresses the `Resend`, `Continue`, and never-started `Send` buttons** — each would be a guaranteed silent no-op on a dead channel (`onSend`/`onContinue` no-op, and a resend only re-stamps the same connection-lost error) — leaving only `Remove` plus the error banner via `FileCard`. On a live channel, transiently failed entries keep a working `Resend`. **The batch "Send all files" button is gated the same way (PR #111).** It is the one send action that escaped the per-file `connectionLost` template gate: with the channel lost it stays live and, on click, re-enters the send pipeline for every `Pending` file — each `onSend` no-ops through the guarded `send()` but re-stamps the connection-lost error plus one toast per file, so a batch click was a toast-burst no-op. The template now wraps the button in `{#if !connectionLost}` (leaving only `Remove`, exactly like the per-file buttons), and `sendAllFiles()` itself returns early on `channelSender.isLost()` as the code-level backstop, mirroring `onContinue`'s dead-channel refusal. [`repo://src/components/sender/Sender.svelte#L45-L59`], [`repo://src/components/sender/Sender.svelte#L356-L365`], [`repo://src/components/sender/Sender.svelte#L335-L349`], [`repo://src/components/sender/Sender.svelte#L456-L471`], [`repo://src/components/sender/SendingFileList.svelte#L1-L45`], [`repo://tests/sender-connection-lost.test.mjs`], [`repo://tests/sender-connection-lost-reactive.test.mjs`], [`repo://tests/sender-resend-connection-lost.test.mjs`]

Chunking: `sendNextChunk` slices `file.slice(offset, offset + chunkBytes)`, reads it as an `ArrayBuffer`, encrypts it (when `isEncrypt` and `aesKey` present), and frames it as a `Message`. The chunk size is **defensively coerced to a number at the slice site** (`Number(chunkSize)` with a 32 KB fallback for non-finite or non-positive values), because a Svelte 5 `<select> bind:value` yields the DOM option value as a **string** — and a string here makes `offset + chunkSize` concatenate instead of add, sending the whole file remainder as one over-sized chunk. The sender options UI also coerces on change: `OfferOptions.onChange` `Number()`s the select value and falls back to `DEFAULT_SEND_OPTIONS.chunkSize` when it is not in `CHUNK_SIZE_OPTIONS`, keeping `sendOptions.chunkSize` a number at the source. **Offset bookkeeping tracks the wire, not the stop flag (PR #114).** `sendBuffer` now **reports whether the chunk actually hit the wire** — it returns `true` when `send()` ran (the chunk is on the wire even if `stop` flipped between encryption finishing and the send), `false` when the stop check bailed before sending — and `sendNextChunk` advances the closure's `offset` only when it did. Skipping the bookkeeping on `stop` used to leave `offset` behind the wire after a stop during the final chunk's send/ack window, so a later `Continue` re-sliced and re-sent the last bytes, which the receiver's exact-size gate rejects as an overshoot on a fully delivered file; progress UI for a removed/aborted entry is cosmetic, so skipping it on stop is safe. [`repo://src/components/sender/Sender.svelte#L197-L291`], [`repo://src/components/OfferOptions.svelte#L19-L30`], [`repo://tests/sender-chunk-size.test.mjs`], [`repo://tests/sender-stop-final-ack.test.mjs`]

**Empty-chunk guard:** if `buffer.byteLength === 0` while `offset < size`, the chunk size is invalid (e.g. a crafted `c` URL param producing NaN/0); the sender aborts with an "Invalid chunk size" error instead of looping forever on zero-byte sends. [`repo://src/components/sender/Sender.svelte#L252-L260`]

Progress: computed as `offset/size * 100`; the reactive `progress` and `bitrate` are only updated every `PROGRESS_UPDATE_UI_STEP` (3) points using a non-reactive `fileStats` mirror — throttling UI updates during fast transfers. Pause/resume is the `stop` flag plus `onContinue`, which re-emits a synthetic `RECEIVED_CHUNK` to restart the loop — except on a dead channel, where `onContinue` no-ops so a resume can't emit a synthetic ack into a pipeline whose next send would just no-op. A Stop during the final chunk's send/ack window is the one case where the stop flag must _not_ stop the pipeline from finishing: the completion ack still walks the handler to `Success` (see the ack-handling step above), so the entry completes instead of parking in `Processing` for a `Continue` that would re-send the last chunk. [`repo://src/components/sender/Sender.svelte#L234-L291`], [`repo://src/components/sender/Sender.svelte#L356-L365`], [`repo://src/configs.ts#L65-L67`], [`repo://tests/sender-stop-final-ack.test.mjs`]

## Receiver state machine

`receivingFiles` is a reactive map; per-file chunk accumulation (`receivingFileChunkMap`), byte/progress counters (`receivingFileStatsMap`), and the per-file processing chains (`chunkQueue`) are **deliberately non-reactive** plain objects to avoid re-rendering per chunk. The guarded send is the same shared `createChannelSender(dataChannel)` helper the sender uses (PR #97): its `isLost()` read gates `onChannelClose` (which calls `markLost()`, see below) and its `send()` no-ops on a dead channel, so once the channel dies no ack/reject can reach the peer and the in-flight/queued pipeline exits quietly. [`repo://src/components/receiver/Receiver.svelte#L29-L35`], [`repo://src/components/receiver/Receiver.svelte#L108-L125`], [`repo://src/utils/channelSender.ts`]

`onMetaData(id, metaData)`:

1. **Register the file entry at `WaitingAccept` first** — before any async work — so the file is visible (and removable) throughout; chunk processing stays safe because the chunk map only exists after the file is accepted.
2. If `isEncrypt && rsa`, unwrap `metaData.key` with the private RSA key into the file's `aesKey` — inside a `try/catch`: on failure the entry gets a visible `error` ("Failed to decrypt the file key"), an error toast fires, and **`EVENT_VALIDATE_ERROR` is sent back to the sender** (its file bounces to `Pending` instead of sitting in `WaitingAccept` forever) before the handler returns without accepting (previously a key-unwrap failure meant the file silently never appeared and the sender waited for an accept that would never come). The success path re-reads and null-guards `receivingFiles[id]` **after** the decryption `await` before assigning `aesKey` (PR #101): the entry is deniable/removable during that window (the list UI shows Accept/Deny on `WaitingAccept` entries since PR #76; `onDeny` deletes the entry), and the unguarded `receivingFiles[id].aesKey` assignment would otherwise throw `Cannot set properties of undefined (setting 'aesKey')` as an unhandled rejection — no toast, no error state, no rejection/validate event for the sender — so the handler now returns quietly when the entry was removed in the window. The key-unwrap **catch** path's `receivingFiles[id].error` write is null-guarded the same way (PR #103): it re-reads `receivingFiles[id]` and returns quietly when the entry was denied/removed during the decryption await, so that second post-await write can no longer throw an unhandled `TypeError` on the `error` assignment (the toast and the `EVENT_VALIDATE_ERROR` bounce that follow would never have run otherwise).
3. Validate via `validateFileMetadata(metaData, receiveOptions.maxSize)` — this also rejects peer-controlled `size` values that are not finite or `<= 0` with "invalid file size" — on failure send `EVENT_VALIDATE_ERROR`, store the error, and stop.
4. If `autoAccept` (default on), immediately `onAccept(id)` — send `EVENT_RECEIVER_ACCEPT`, set `Processing`, and initialize the chunk/stats maps. Manual accept/deny is also available via the list UI: an entry that failed key decryption or validation stays in `WaitingAccept` with its `error` shown, so it remains actionable (Deny/Remove, and an Accept that is refused — see below) instead of dead-ending on Remove only. [`repo://src/components/receiver/Receiver.svelte#L37-L99`], [`repo://src/components/receiver/ReceivingFileList.svelte#L18-L32`], [`repo://src/configs.ts#L60-L63`], [`repo://src/utils/validator.ts#L1-L17`], [`repo://tests/receiver-metadata-size.test.mjs`], [`repo://tests/receiver-key-decryption-failure.test.mjs`]

**`onAccept` refuses metadata-failed entries (PR #78).** `onAccept` is the shared entry point for both `autoAccept` and the list UI's Accept button, and it now guards up front: an entry whose metadata failed — `error` set (key decryption or max-size validation) or an encrypted session with no `aesKey` — is **not** accepted. Instead it fires an explanatory error toast ("Cannot accept <name>: the metadata/key failed to process — the sender must resend the file"), sends `EVENT_RECEIVER_REJECT`, leaves the entry in `WaitingAccept` + `error` (Deny/Remove remain available), and creates **no** chunk map (so late-arriving chunks are dropped by the `onChunkData` guard instead of counting ciphertext toward `receivedSize`). Without a usable key the transfer can never succeed: on an encrypted session `processChunk` would either skip decryption and assemble the raw ciphertext as a `Success` blob, or every chunk would hit `rejectCorruptChunk` (an N-toast storm per resend), and the sender — already bounced to `Pending` by `EVENT_VALIDATE_ERROR` — would sit in `WaitingAccept` for a file it can never deliver. Only entries that pass the guard emit `EVENT_RECEIVER_ACCEPT`, flip to `Processing`, and get their chunk/stats maps. [`repo://src/components/receiver/Receiver.svelte#L339-L384`], [`repo://tests/receiver-key-decryption-failure.test.mjs`]

`onChunkData(id, chunk)` is now **synchronous**:

1. **Guard**: drop the chunk for unknown or uninitialized file ids (metadata never registered, file removed/denied, or file already completed) instead of throwing on a missing entry inside queued processing.
2. **Enqueue onto the per-file promise chain** via `serializeTask(chunkQueue, id, …)` (`src/utils/serialize.ts`): `processChunk` for chunk N+1 cannot start before chunk N's processing has settled, so the post-await work — decrypt, push to `receivedChunks`, stats, blob-on-complete — runs strictly in arrival order even when WebCrypto `decryptAesGcm` calls complete out of order (which is what silently corrupted encrypted files before this fix). The chain's `catch` routes any error to `rejectCorruptChunk` (idempotent — no-op once the file's chunk map is gone) instead of silently swallowing it, so a failed chunk can never leave the file permanently incomplete. [`repo://src/components/receiver/Receiver.svelte#L152-L175`], [`repo://src/utils/serialize.ts#L1-L20`]

`processChunk(id, receivingFile, chunk)`:

1. **Decrypt first (when encryption applies), fail visibly:** a chunk that fails AES-GCM auth routes to `rejectCorruptChunk` — it marks the file errored, bounces the status back to `Pending`, toasts the failure, sends `EVENT_RECEIVER_REJECT` so the sender stops cleanly instead of waiting for acks forever, and tears down the per-file chunk/stats/queue state — instead of the chunk being silently dropped and the byte count never reaching the total, which would have left the file in `Processing` forever (PR #54).
2. **Re-check the chunk map**: if the file was removed/denied/rejected while this chunk was in flight, drop the result without acking (an ack would advance the sender past a rejected file).
3. **Immediately** send `EVENT_RECEIVED_CHUNK` — the sender's next chunk only flows after this ack, which paces the transfer (backpressure). The ack is sent **only after successful decryption**, so a corrupt chunk never advances the sender.
4. Append the plaintext buffer to `receivedChunks`, bump `receivedSize` and throttled progress/bitrate (same 3-point step).
5. **Completion gate is an exact byte match**: the receiver flips the file to `Success` only when `receivedSize === metaData.size` (not `>=`). Because `metaData.size` is peer-controlled and the validator cannot bound the payload against it, a peer that claims a size smaller than the payload it actually streams is corrupt; finishing on the first chunk that merely reached the claim would mark a silently truncated prefix as `Success` while the stream tail is dropped on both ends. When the gate fires, the file `Blob` is built **immediately and both per-file maps are deleted** — this releases the raw per-chunk buffers so a large file is not held twice in memory — then status → `Success`, toast, and release the file's `chunkQueue` entry. The `EVENT_RECEIVED_CHUNK` ack itself goes through the guarded `send()`: on a dead channel it silently fails instead of throwing `InvalidStateError` into the chunk pipeline (the file has already been marked "connection lost" by `onChannelClose`, so no per-chunk error may fire for chunks that only failed because the channel closed mid-transfer). [`repo://src/components/receiver/Receiver.svelte#L248-L272`], [`repo://src/components/receiver/Receiver.svelte#L263-L272`]
6. **Overshoot reject**: when a chunk pushes `receivedSize` past `metaData.size` without ever hitting the exact value, the declared size is a lie — the receiver now rejects the whole file instead of assembling a truncated prefix. `rejectOversizedStream` sets the error ("peer stream did not match the declared size — file rejected: got N bytes, declared M") and toast and delegates the teardown to the shared `rejectFile` helper (below). [`repo://src/components/receiver/Receiver.svelte#L300-L315`], [`repo://tests/receiver-metadata-size.test.mjs`]

**Shared reject teardown (`rejectFile`, PR #94).** `rejectOversizedStream` and `rejectCorruptChunk` previously each carried the same ~25 lines of copy-pasted teardown that had to stay in sync; they now both delegate to one shared `rejectFile(id, receivingFile, error, toastMessage)` helper (the call sites are thin wrappers that just supply the error and toast message). The helper guards on `receivingFileChunkMap[id]` as source of truth (no-op if the file is no longer being actively received — removed, denied, or already rejected), sets the entry's `error`, bounces the status back to `Pending` (so the file remains removable/retryable and the error is visible), toasts, sends `EVENT_RECEIVER_REJECT` via the guarded `send()` so the sender bounces to `Pending` instead of reporting a successful transfer, and tears down the per-file chunk/stats/queue state so in-flight chunks for this file are dropped. The error/status mutations propagate through the same `$state` proxy as `receivingFiles[id]`, so the UI updates without any extra assignment. `tests/receiver-metadata-size.test.mjs` follows the delegation when it extracts the `rejectOversizedStream` body, so the assertions land on the body that actually performs the teardown. [`repo://src/components/receiver/Receiver.svelte#L280-L324`], [`repo://tests/receiver-metadata-size.test.mjs`]

Removal/deny sends `EVENT_RECEIVER_REJECT` (if not already successful, via the guarded `send()` so it cannot throw on a dead channel) and drops the file's state maps **and its `chunkQueue` entry** (likewise cleared in `onAccept` for re-accept, and by `rejectCorruptChunk` on a corrupt chunk). [`repo://src/components/receiver/Receiver.svelte#L300-L375`]

**Connection loss tears down the pipeline, not just the link state.** `onChannelClose` (fired by the page's `dataChannel` `onclose`/`onerror`) calls the shared helper's `markLost()` (guarded by `isLost()` so it runs at most once) and marks every non-`Success` file with a single "connection lost — transfer aborted" error (status → `Pending`), and deletes every per-file chunk/stats/queue entry so queued chunks are dropped by `onChunkData` instead of re-entering `processChunk` — the old handler only reset the page's link state, leaving files in `Processing` forever and queued chunks re-firing false "corrupt chunk" errors. [`repo://src/components/receiver/Receiver.svelte#L121-L135`], [`repo://tests/receiver-connection-lost.test.mjs`]

## Downloading received files

Single-file and bulk download both route through `triggerDownload`, which creates an object URL, clicks a temporary `<a download>`, and **defers `URL.revokeObjectURL` ~1 s** — revoking in the same tick can abort the async download in some engines (Firefox may start the fetch after the revoke). [`repo://src/components/receiver/Receiver.svelte#L318-L337`]

"Download all files (zip)" no longer triggers sequential per-file raw downloads (which browsers block after the first, and which never produced a zip despite the label): it collects all `Success` files without errors and builds a **real store-only ZIP archive in memory** via `createZipStoreOnly` (`src/utils/zip.ts`, no new dependency — a hand-rolled uncompressed/method-0 writer with CRC-32, UTF-8 name flag, and duplicate-name disambiguation), saving a single `zero-share-files.zip`. `onDownload` null-guards the entry (a missing/duplicated key, e.g. from a race with `onRemove`, no longer throws an unhandled `TypeError` and skips the per-file teardown — the file is simply not found). The duplicate-name disambiguation in `uniqueNames` checks each candidate against every **already-emitted final name** (a `Set`), not a per-base occurrence counter: names are peer-controlled, so the generated `"base (n)"` suffix must not collide when the input already contains a pre-suffixed name (e.g. `"report.pdf"`, `"report.pdf"`, `"report.pdf (1)"` — the old counter would emit `"report.pdf (1)"` twice). **Peer-controlled entry names are sanitized on the way in, not just deduped.** `Receiver.onMetaData` now runs `metaData.name = sanitizeName(metaData.name)` as its first action (PR #98) — one ingestion rule covering every sink (the bulk ZIP and `<a download>` in `triggerDownload`). `sanitizeName` keeps only the safe basename (last segment across `/`, `\`, and U+2215), drops NUL + C0 control + DEL by code point (astral/emoji names survive), collapses dot runs, and falls back to `"file"` on an empty result — so a peer naming a file `a/b/../../../../etc/cron.d/evil` can no longer make a standard extractor resolve it outside the archive folder (zip-slip / CWE-22) and overwrite arbitrary user-writable files on extract. `createZipStoreOnly`/`uniqueNames` re-sansitize as defense in depth, so the ZIP writer is safe even if a future caller passes a raw peer name. **The bulk zip is capped by the classic-ZIP per-entry ceiling.** `createZipStoreOnly` writes no zip64 extra fields, so any entry of 4 GiB or more (`0xffffffff`, the "size in zip64" sentinel) or an archive whose central directory starts past that value would silently corrupt; it now **throws explicitly** for both conditions instead of emitting a corrupt archive (PR #110). [`repo://src/components/receiver/Receiver.svelte#L38-L48`], [`repo://src/components/receiver/Receiver.svelte#L384-L410`], [`repo://src/components/receiver/Receiver.svelte#L457-L497`], [`repo://src/utils/zip.ts#L28-L53`], [`repo://src/utils/zip.ts#L82-L119`], [`repo://tests/zip.test.mjs`], [`repo://tests/receiver-zip-download.test.mjs`]

## Validation & user-facing errors

`validateFileMetadata` is the single size gate (returns an `Error` with a `humanFileSize`-rendered limit message; undefined when OK). It enforces **two** bounds, because `metaData.size` is peer-controlled and is the receiver's "done" gate: a `size` that is not finite or is `<= 0` is rejected with an explicit "invalid file size" error (previously a peer-claimed `size` of 0/negative/NaN would make the receiver flip the file to `Success` on the first chunk with a partial/empty payload, or drive the progress math NaN/negative and break the progress UI), and `size > maxSize` fails with the limit message (default max 1 GB via `DEFAULT_RECEIVE_OPTIONS.maxSize`). Sender-side validation runs at pick time without a limit; receiver-side enforces both bounds in `onMetaData` after key handling — any failure sends `EVENT_VALIDATE_ERROR` to the sender. Errors surface through the nanostores `toastAtom` via `addToastMessage`, which both components import. [`repo://src/utils/validator.ts#L1-L17`], [`repo://src/components/receiver/Receiver.svelte#L80-L94`], [`repo://src/stores/toastStore.ts`], [`repo://tests/receiver-metadata-size.test.mjs`]

**Progress is clamped to [0, 100] on the receiver.** A peer that claims a size smaller than the payload it actually streams would push the progress ratio past 100 (NaN is coerced to 0 as a safe fallback), so the receiver clamps before handing the value to the UI. [`repo://src/components/receiver/Receiver.svelte#L222-L246`]

**Max Size options must be true byte values and stay under the classic-ZIP ceiling (PR #44, PR #110).** `ReceiverOptions.svelte`'s "Max Size" dropdown options used to carry values 1024x smaller than their labels — "10 MB" was `10 * 1024` (10 KB), so selecting it rejected nearly every real file. The options now carry the values their labels mean: **10 MB / 100 MB / 1 GB / 2 GB** — `DEFAULT_RECEIVE_OPTIONS.maxSize` stays 1 GB when nothing is selected. The **largest option is now 2 GB, not the former "10 GB" / "Unlimit" (1 TiB)**: `createZipStoreOnly` writes no zip64 extra fields, so the classic-ZIP per-entry ceiling is ~4 GiB, and the old 10 GB / Unlimit values made the "Download all files (zip)" path **silently impossible for their own allowed sizes** — an allowed 10 GB file simply could never be bulk-zipped. A second, silent bug was fixed in the same pass: `bind:value` on a `<select>` yields the DOM option value as a **string** after user interaction, and the raw string broke `humanFileSize` rendering (`Number.isFinite` fails → "0 B" in error toasts); `onChange` therefore coerces with `Number(maxSize)` and falls back to `DEFAULT_RECEIVE_OPTIONS.maxSize` when the parse is not finite, keeping `ReceiveOptions.maxSize` a number at runtime. [`repo://src/components/receiver/ReceiverOptions.svelte#L41-L57`], [`repo://src/configs.ts#L60-L66`], [`repo://src/utils/zip.ts#L82-L119`], [`repo://tests/receiver-options-size.test.mjs`]

## Invariants & failure behavior

- **Chunk order is protocol- and runtime-enforced, not channel-ordered**: the data channel is created `ordered: false`; correctness now rests on two layers — the single-writer sender loop per file (one `RECEIVED_CHUNK` → one chunk, sender stays one round-trip ahead) AND the receiver's per-file promise-chain serialization (`serializeTask`), which guarantees receiver-side assembly happens in strict arrival order even when WebCrypto decrypt completions are out of order. [`repo://src/components/OfferPage.svelte#L112-L114`], [`repo://src/utils/serialize.ts#L1-L20`], [`repo://src/components/receiver/Receiver.svelte#L101-L175`]
- A receiver ack for a stopped/idle file (stop with bytes still to send, or a non-`Processing` entry that isn't finished) resets the sender file to `Pending` with progress 0 rather than erroring — **except** a `stop` with `offset >= size` (Stop clicked during the final chunk's send/ack window), which completes the entry to `Success`: the last chunk is already on the wire, so the completion ack must finish the file or a later `Continue` would re-send the last chunk and the receiver's exact-size gate would reject the fully delivered file as an overshoot (PR #114). An entry already at `Success` is terminal — no ack (stray or synthetic) can bounce it back to `Pending`.
- **Removing an in-flight sender file is safe**: `onRemove` sets `stop` before deleting the entry, the chunk pipeline only dereferences the entry captured at `onSend` (never a live re-read of `sendingFiles[key]` after an await), re-checks `stop`/the live entry at every await boundary, and the event handlers bail if the live entry is gone — so no continuation can dereference a deleted entry or send into the void. [`repo://src/components/sender/Sender.svelte#L335-L365`], [`repo://src/components/sender/Sender.svelte#L197-L291`], [`repo://tests/sender-remove-inflight.test.mjs`]
- **Connection loss (PR #74)**: a closed/errored data channel fires `onChannelClose` on both sides — the sender marks every non-`Success` file "connection lost — transfer aborted" (one toast per file, `Processing` files stopped) and the receiver does the same while tearing down every per-file chunk/stats/queue entry; guarded `send()` no-ops on a dead channel instead of throwing `InvalidStateError` into a chunk/ack pipeline, so a mid-transfer close no longer produces misleading "corrupt chunk" / "Failed to send chunk: InvalidStateError…" errors, unhandled rejections, or files stuck in `Processing`. [`repo://src/components/sender/Sender.svelte#L51-L72`], [`repo://src/components/receiver/Receiver.svelte#L113-L150`], [`repo://tests/sender-connection-lost.test.mjs`], [`repo://tests/receiver-connection-lost.test.mjs`]
- **Late/stray chunks are dropped, not fatal**: chunks for unknown/uninitialized file ids are ignored at the `onChunkData` guard, and `processChunk` re-checks the chunk map after the decrypt await (a file may be removed/denied mid-flight) — but a chunk that fails decryption is **not** dropped: it rejects the whole file visibly via `rejectCorruptChunk` (error + `Pending` + `EVENT_RECEIVER_REJECT` + per-file state teardown), because without retransmission a missing byte can never make the file complete. [`repo://src/components/receiver/Receiver.svelte#L152-L175`], [`repo://src/components/receiver/Receiver.svelte#L182-L298`]
- Completion is exact-size based: both sides stop when the declared `metaData.size` is fully sent/received; there is no file trailer or checksum, so integrity relies on GCM authentication (encryption on) or DTLS data integrity. The receiver additionally clamps its progress to [0, 100] so a peer-claimed size smaller than the streamed payload cannot push the ratio off-scale.
- **`MetaData.size` is `int64` on the wire and receiver-validated** (PR #42 / commit 721c502 widened it from `int32`): files of 2 GiB or larger no longer throw `invalid int32` during `Message.encode`, and the receiver's `validateFileMetadata` now rejects peer-controlled `size` values that are not finite or `<= 0` with "invalid file size", so a malicious/buggy peer can no longer complete a file with a partial/empty payload. [`repo://src/proto/message.proto#L1-L8`], [`repo://src/utils/validator.ts#L4-L13`], [`repo://tests/protocol-size.test.mjs#L33-L52`], [`repo://tests/receiver-metadata-size.test.mjs`]
- **A metadata-failed entry can never be force-accepted (PR #78).** `onAccept` (the shared entry point of `autoAccept` and the list UI's Accept button) guards up front: an entry with `error` set or an encrypted session without `aesKey` is refused — explanatory toast, `EVENT_RECEIVER_REJECT`, entry stays `WaitingAccept` + `error` (Deny/Remove remain the real exits), and **no chunk map is created**, so late-arriving chunks are dropped by the `onChunkData` guard. Without a usable key the transfer can never succeed: an encrypted session would either assemble the raw ciphertext as a `Success` blob or hit `rejectCorruptChunk` on every chunk (an N-toast storm per resend), and the sender — already bounced to `Pending` by `EVENT_VALIDATE_ERROR` — would otherwise sit in `WaitingAccept` for a file it can never deliver. Pinned by `tests/receiver-key-decryption-failure.test.mjs` (extended in PR #78 with a full `onAccept` mirror and a static source guard). [`repo://src/components/receiver/Receiver.svelte#L339-L384`], [`repo://tests/receiver-key-decryption-failure.test.mjs`]
