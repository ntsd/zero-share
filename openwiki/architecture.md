# Architecture: Serverless WebRTC P2P Sharing

Zero Share is a **serverless, client-side P2P file-sharing web app**: two browsers connect directly over a WebRTC data channel and transfer files with no application backend. The only third-party network dependency is public STUN servers used for ICE candidate discovery.

## System boundaries

- **Static frontend, no server.** The app is an Astro site built in `output: 'static'` mode with Svelte (`client:only`) interactive components; deployment produces plain static files (GitHub Pages or `npm run build`). There is no server-side code and no relay server of any kind. [`repo://astro.config.mjs#L8-L13`]
- **Two routes, two roles.** `/` renders `OfferPage` (the initiator) and `/receive` renders `ReceivePage` (the responder). Both routes are thin Astro pages that mount a single Svelte component under the shared `MainLayout`. [`repo://src/pages/index.astro#L1-L10`], [`repo://src/pages/receive.astro#L1-L10`]
- **Dual-role transfer UI.** After the data channel opens, _each_ page mounts **both** a `Sender` and a `Receiver` and the user toggles between Send/Receive modes — either peer can transfer files in either direction over the same channel. [`repo://src/components/OfferPage.svelte#L398-L409`], [`repo://src/components/ReceivePage.svelte#L259-L293`]
- **Shared ICE-server resolution.** Peer connections are configured with a single ICE server (default `stun:stun.l.google.com:19302`, selectable from a built-in STUN list or a user-typed custom value). The value is resolved through the shared `isSupportedIceServer` / `resolveIceServer` predicates in `src/configs.ts`, which accept the built-in allowlist **plus any well-formed `stun:`/`turn:` URL** — and the sender enforces them on what it emits into the `i` link param **and** on its own `RTCPeerConnection`, while the receiver enforces the same predicate on what it accepts, so a custom/TURN server chosen on the sender is always honored by the peer and the two sides can never end up on different servers. Anything else falls back to the default with an error toast on both sides. There is no built-in TURN fallback list beyond the user-supplied value, and no relay server of any kind. [`repo://src/configs.ts#L3-L20`], [`repo://src/configs.ts#L47-L54`], [`repo://src/components/OfferPage.svelte#L75-L108`], [`repo://src/components/ReceivePage.svelte#L62-L77`]

## Control flow (connection establishment)

1. The **offer** peer creates an `RTCPeerConnection` (with the shared-predicate-resolved ICE server), opens a data channel (`ordered: false` — ordering is handled by the message protocol), generates a local offer, and encodes the SDP into a shareable `?s=...` link on the `/receive` route. Link generation waits for ICE candidates to finish, with a 3-second timeout fallback; the two build paths are guarded by a per-invocation `offerBuilt` flag so the link is built at most once, and the RSA keypair is minted **exactly once** at the top of `generateOfferLink()` (before the peer exists) so the timeout fallback can never rotate the key under an already-built link. Regeneration is generation-safe: `generateOfferLink` first tears down the previous generation — clears the pending ICE-candidate timer, nulls the handlers and closes the old data channel and `RTCPeerConnection` (unless already closed), resets the settled peer crypto (`rsaPub = undefined` and `effectiveEncrypt` re-pinned from the live setting) and the dead generation's UI state (new-file badge, `isConnecting`, pending answer code) — then bumps a monotonically increasing `offerGeneration` token; the timeout fallback re-checks that token at fire time, so a stale timer left over from a previous generation (whose closure holds the old public key) can never build a link from the new peer's SDP. Synchronous construction or offer-creation failures are caught, surfaced with a toast, **and — since PR #108 — the just-created generation is torn down with the same guarded shape as the regeneration teardown above**: the pending ICE-candidate timer is cleared, the new data channel's four handlers are nulled before `dataChannel.close()` (and the variable reset to `undefined`), and the new `RTCPeerConnection` is closed guarded on `connectionState !== 'closed'` (when the failure happened before the peer/channel existed both guards skip and the still-closed previous generation is left untouched) — leaving the failed peer's ICE agent, UDP sockets, and STUN/TURN keepalives live until the next generation or page unload, and a stale answer-code paste running `setRemoteDescription` against the dead peer. The offer page therefore now has **four** guarded `connection.close()` call sites (the two channel-death handlers, the regeneration teardown, and the offer-creation catch) — `tests/dead-channel-peer-close.test.mjs` pins that count. The teardown block also **clears the dead generation's offer link** (`offerLink = ''`, alongside `showNewFile` / `isConnecting` / `answerSDP` reset and before `generating = true`): that link's SDP belongs to the peer just closed and its `p` key to the RSA keypair about to be re-minted, so it is dead in every sense — even a somehow-answered handshake would break encrypted transfers, and `acceptAnswer()` would apply the answer to the NEW peer (still in `stable` signaling state) and reject every answer from a peer who opened the stale link. Resetting it in the teardown — not only the catch — guarantees a failed regeneration returns to the clean "generate" state with no dead link to copy/QR/accept, and the template's `offerLink !== ''` gate (encryption lock + Accept-Answer section) re-locks/unlocks with the actual live link. [`repo://src/components/OfferPage.svelte#L164-L295`], [`repo://src/components/OfferPage.svelte#L68-L101`], [`repo://src/components/OfferPage.svelte#L230-L244`], [`repo://tests/offer-peer-lifecycle.test.mjs`], [`repo://tests/regen-offer-stale-peer-crypto.test.mjs`]
2. The **answer** peer opens the offer link, decodes the SDP from the URL, and sets it as the remote offer — inside `try/catch`, since `s` is user-controllable via the shared link and `sdpDecode` throws synchronously on empty, invalid-base64, or non-SDP input, so a crafted link surfaces an "Invalid SDP in link" error toast instead of crashing the whole page during load (PR #45). The promise of that step is kept and **awaited before `createAnswer`** (with a `signalingState === 'have-remote-offer'` check): without this, a rejected `setRemoteDescription` would leave the answer queued against a connection that can never answer, and the "Generating Answer" spinner would spin forever with zero feedback. Before freezing the answer it awaits the import of the offer peer's RSA key from the `p` param; a malformed key downgrades the session to plaintext (with an error toast) so the answer never advertises encryption the peer cannot honor, and produces an **answer code** = `sdpEncode(answerSdp) + '|' + base64(RSA public key)` (empty key portion when downgraded). The same 3-second ICE-candidate timeout fallback applies. [`repo://src/components/ReceivePage.svelte#L46-L59`], [`repo://src/components/ReceivePage.svelte#L138-L178`], [`repo://src/components/ReceivePage.svelte#L246-L256`]
3. The offer peer pastes (or QR-scans) the answer code. `acceptAnswer` first refuses to signal a **dead peer**: if the channel's `onerror`/`onclose` handler already ran (or the peer was closed by a racing regeneration), the handler toasts "Connection lost — generate a new offer to connect" and returns before parsing, instead of applying the answer to a closed peer — which would only fail inside the `try/catch` with a misleading "Invalid answer code" (PR #104). [`repo://src/components/OfferPage.svelte#L394-L398`]. Then, when encryption is on, it parses the code (`parseAnswerCode` splits on the last `|`): a well-formed code with an **empty** key portion means the receiver deliberately downgraded to plaintext, so the offer peer follows it into plaintext (info toast, `effectiveEncrypt = false`) instead of bailing on the empty key and dead-ending the handshake; a missing separator or a damaged non-empty key still toasts an error and aborts, instead of leaving a half-configured connection. A key **present** in the code pins the session to encrypted (`effectiveEncrypt = true`) — the answer's key portion, not the live setting, is the source of truth for this session's encryption. Then the answer is applied as the remote description — likewise inside a `try/catch`, since the pasted/scanned SDP may be malformed and would otherwise escape as an unhandled rejection with no visible error (PR #45). Once `dataChannel.onopen` fires, the transfer UI unlocks on both sides. [`repo://src/components/OfferPage.svelte#L281-L344`]

**Clipboard copy is guarded (PR #79).** The manual-exchange copy buttons — `copyOfferLink` on the offer page and `copyAnswerCode` on the receive page — wrap `navigator.clipboard.writeText` in `try/catch`: a rejection (non-secure context, denied permission, unavailable API) toasts "Copy failed — select the … text and copy it manually" instead of escaping as an unhandled rejection, so a user who believes they copied the link/answer code actually did. [`repo://src/components/OfferPage.svelte#L297-L307`], [`repo://src/components/ReceivePage.svelte#L164-L174`], [`repo://tests/clipboard-copy-robustness.test.mjs`]

SDP text is made URL-safe by `sdp-compact` compaction plus character substitutions (`/`→`_`, `+`→`~`, `=`→`-`), keeping share links short and safe. `sdpDecode` throws synchronously on malformed input (empty, invalid base64, or a decompressed payload that is not SDP), so every caller must guard with `try/catch`. See `subsystems/peering.md` for the full link and code formats.

## Data flow (file transfer)

All traffic on the data channel is **proto3-framed `Message` bytes** — no ad-hoc text protocol. A `Message` carries a `file id` plus exactly one of:

- `metaData` — file name, size (int64 on the wire — commit 721c502 / PR #42 widened it from int32 so files ≥ 2 GiB no longer throw `invalid int32` during `Message.encode`), MIME type, and the RSA-wrapped per-file AES key (encryption mode only);
- `chunk` — a raw (or encrypted) slice of the file body;
- `receiveEvent` — receiver→sender control events (`ACCEPT`, `REJECT`, `RECEIVED_CHUNK`, `VALIDATE_ERROR`). [`repo://src/proto/message.proto#L1-L31`]

Both pages dispatch incoming messages through the shared `handlePeerMessage` helper in `src/utils/peerMessage.ts` (deduplicated from the two identical per-page handlers in PR #71), with the same oneof switch on `metaData` / `chunk` / `receiveEvent`, routing to `Receiver.onMetaData`, `Receiver.onChunkData`, or `Sender.onReceiveEvent`. The `Message.decode` call on peer-controlled data-channel bytes is wrapped in `try/catch` inside the helper: a malformed or truncated protobuf frame makes `decode` throw synchronously, which would otherwise crash the page uncaught (PR #46) — instead the frame is dropped and an "Invalid message from peer" toast fires. **Binary frames are real bytes, not Blobs:** both pages pin `dataChannel.binaryType = 'arraybuffer'` immediately at channel acquisition (the offer side at the `createDataChannel` site, the answer side at the `ondatachannel` site, before the `onopen` wiring), because WebRTC's default `binaryType` is `'blob'` — with it every binary frame would arrive as a `Blob`, `new Uint8Array(blob)` in `handlePeerMessage` would yield a zero-length view, `Message.decode` would silently produce an empty message, and _every_ frame would be dropped (a guaranteed no-op transfer, PR #95). Both pages additionally wire the data channel's `onerror`/`onclose` to `sender?.onChannelClose()` and `receiver?.onChannelClose()`, so a dead channel marks in-flight/queued files "connection lost" and stops their pipelines instead of leaking `InvalidStateError` into chunk pipelines as misleading per-chunk failures (PR #74) — and, since PR #104, **close the `RTCPeerConnection` itself**: closing the data channel alone leaves the peer's ICE agent, UDP sockets, and STUN/TURN keepalives live until the browser's ICE timeout or page unload (the same leak the offer page's regeneration teardown has always handled for its dead peer), so both `onerror` and `onclose` additionally call `connection.close()` guarded on `connectionState !== 'closed'` — `close()` throws `InvalidStateError` on an already-closed peer, which an error+close double-fire or a racing regeneration would otherwise surface. `tests/dead-channel-peer-close.test.mjs` statically pins the guarded `close()` in both pages' handlers plus the handlers' existing `onChannelClose()` calls. [`repo://src/utils/peerMessage.ts`], [`repo://src/components/OfferPage.svelte#L145-L185`], [`repo://src/components/ReceivePage.svelte#L122-L157`], [`repo://tests/peer-message-handler.test.mjs`], [`repo://tests/dead-channel-peer-close.test.mjs`]

**Outgoing frames go through one shared guarded-send helper.** The copy-pasted guarded data-channel `send` (dead-channel flag + `readyState` check + throwing-send `catch`) that lived separately in `Sender.svelte` and `Receiver.svelte` is now the `createChannelSender(dataChannel)` factory in `src/utils/channelSender.ts` (PR #97, mirroring the `peerMessage.ts` handler dedup): it returns `{ send(message), isLost(), markLost() }` — `send` no-ops with `false` when the lost flag is set or `readyState !== 'open'`, returns `true` on a successful send, and on a throwing send flips the lost flag and returns `false` instead of letting an `InvalidStateError` escape; `markLost()` is the idempotent flip fired by the owning component's `onChannelClose()`; `isLost()` is the helper's live read. The sender's `connectionLost` flag is a plain **`$state`** that the template reacts to — **not** a `$derived` over `channelSender.isLost()`, which would cache `false` forever (a `$derived` evaluates against the signals it reads; `isLost()` reads a plain closure variable, so such a `$derived` would be permanently clean) — flipped by `onChannelClose()` and by a thin `send()` wrapper that mirrors the helper's lost flag into it, so the file-list UI gate and `onContinue`'s dead-channel refusal re-render on the dead-channel close instead of staying stale (PR #109). [`repo://src/utils/channelSender.ts`], [`repo://src/components/sender/Sender.svelte#L24-L49`], [`repo://src/components/receiver/Receiver.svelte#L108-L124`], [`repo://tests/channel-sender.test.mjs`]

The transfer protocol is **receiver-ack chunking**: the sender emits metadata, waits for `RECEIVER_ACCEPT`, then sends chunks one per `RECEIVER_RECEIVED_CHUNK` acknowledgment — a simple backpressure loop that paces the transfer. File lifecycle is modeled per file as `Pending → WaitingAccept → Processing → Success` with error/reject returns to `Pending`. The receiver's `onAccept` entry point is guarded (PR #78): an entry whose metadata failed — its `error` is set, or an encrypted session with no `aesKey` — is refused with an explanatory toast plus `EVENT_RECEIVER_REJECT` (the entry stays in `WaitingAccept` so Deny/Remove remain available), because without a usable key the transfer can never succeed. `onAccept` also bails on a **null + status guard** before the ACCEPT send — `if (!receivingFile || receivingFile.status !== FileStatus.WaitingAccept) return;` — so a second Accept click that lands in the same frame as the first (before Svelte re-renders the button away) no longer sends a second `EVENT_RECEIVER_ACCEPT` or re-initializes the per-file chunk state (which previously drove the sender's persistent ACCEPT handler to fire `sendNextChunk()` concurrently, putting the same chunk on the wire twice; PR #117, `tests/receiver-double-accept.test.mjs`). The completion gate is an **exact byte match**: the receiver flips a file to `Success` only when `receivedSize === metaData.size` (not `>=`), and when a chunk pushes `receivedSize` past the declared size the whole file is rejected via `rejectOversizedStream` instead of being marked complete from a truncated prefix. See `subsystems/file-transfer.md`.

## Security layering

1. **DTLS** — inherent to WebRTC; protects the data channel in transit but is exposed to MITM on the SDP offer/answer exchange (the links are unauthenticated).
2. **Optional application-layer encryption** — when enabled, each file is encrypted with its own **AES-256-GCM** key, and that key is wrapped with the receiver's **RSA-OAEP-2048** public key and delivered inside the `metaData` message. This makes file content confidential even if the SDP exchange is intercepted. It is off by default (`isEncrypt: false`). The offer side tracks the effective session encryption in `effectiveEncrypt`: while no offer link exists, `onOptionsUpdate` re-syncs it from the live setting (and clears any imported peer key); once the link is live the session's mode is **settled** by the handshake — the accepted answer's key portion pins it (present = encrypted, empty = plaintext) — so a post-generation settings toggle (chunk size, ICE server, or a synthetic encryption flip) must not desync the Sender/Receiver from the peer's settled mode. [`repo://src/utils/crypto.ts#L1-L11`], [`repo://src/components/OfferPage.svelte#L38`], [`repo://src/components/OfferPage.svelte#L287-L367`], [`repo://src/configs.ts#L41-L45`]. See `subsystems/encryption.md`.

## State model

File state is held entirely in client memory (Svelte 5 `$state` maps keyed by file id — `crypto.randomUUID()` on the sender side, so same-named files never collide). Reactivity-sensitive UI state (progress, bitrate) is throttled by keeping per-file stats in **non-reactive** maps and flushing to reactive state every `PROGRESS_UPDATE_UI_STEP` (3) percentage points, avoiding render storms during transfers. The per-side `connectionLost` flag is **not** an independent copy on each side: both `Sender` and `Receiver` create a `createChannelSender(dataChannel)` (see the data-flow section above) — the **sender** keeps a plain **`$state`** `connectionLost` that the template reacts to, flipped by `onChannelClose()` and by a thin `send()` wrapper mirroring the helper's lost flag (a `$derived` over `channelSender.isLost()` would cache `false` forever because `isLost()` reads a plain closure variable, not a Svelte signal — PR #109), while the **receiver** gates on the helper's `isLost()` read directly — so the dead-channel flag, the guarded `send()`, and the UI gating all read one shared source of truth rather than two copies that must be kept in sync. [`repo://src/type.ts#L1-L78`], [`repo://src/components/sender/Sender.svelte#L22-L49`], [`repo://src/components/receiver/Receiver.svelte#L25-L35`], [`repo://src/configs.ts#L65-L67`]

There is **no persistence**: received files are assembled into `Blob`s held in memory and downloaded on demand; nothing is stored in IndexedDB, localStorage, or server-side.
