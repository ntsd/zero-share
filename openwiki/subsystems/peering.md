# Subsystem: WebRTC Peering and SDP Links

Peering is the connection-establishment layer: it turns two browsers into connected WebRTC peers using only **shareable artifacts** — an offer link and an answer code. No signaling server exists.

## SDP encoding for URL transport

Raw SDP is not URL-safe and is long. `sdpEncode` compacts it with `sdp-compact` (`compactSDP`) and substitutes RFC-3986-unsafe characters: `/`→`_`, `+`→`~`, `=`→`-`. `sdpDecode` reverses the substitutions before `decompactSDP`, with an `isOffer` flag matching the SDP role. This keeps links short and copy/paste/QR friendly. `sdpDecode` **throws synchronously** on malformed input — empty string, invalid base64, or a decompressed payload that is not SDP (PR #45 documented the contract in source; `tests/sdp-robustness.test.mjs` transpiles the real `sdpEncode`/`sdpDecode` module from `src/utils/sdpEncode.ts` and pins that `sdpDecode` still throws on malformed input), so every caller of user-controllable input must guard it with `try/catch`. [`repo://src/utils/sdpEncode.ts#L1-L14`], [`repo://tests/sdp-robustness.test.mjs`]

## Offer link contract (`/receive?s=...&i=...&c=...&p=...`)

The offer page builds the link with `buildURL` (base-URL/path join + query-param serialization; empty values are omitted; the former `joinPath`/`buildURLParams` helpers were dead exports, removed in a YAGNI pass), together with the two deployment-base helpers `appBaseFrom` and `receiveBounceTarget`: [`repo://src/utils/path.ts`], [`repo://src/components/OfferPage.svelte#L75-L109`]

The offer link itself is built with `buildURL(appBaseFrom(location.href), 'receive', { s, i, c, p })` inside `createSDPLink` — the base is the app's **deployment base**, not `location.href`'s origin or raw value: `appBaseFrom` takes the URL's origin plus the pathname up to and including its last `/` (the containing directory of the offer page, which is always the deployment's base-root page), dropping the query string, the fragment, and any incidental leaf component (e.g. `index.html`) in one step. That derivation carries two contracts at once. **Fragment stripping (PR #120):** the app's pages deep-link with fragments (both `OfferPage` and `ReceivePage` render `GITHUB_LINK + '#how-does-it-work'`), and the original query-only strip (`location.href.split('?')[0]`) left a fragment in the base that would land **before** `/receive` in the generated link — URL parsing treats everything after `#` as a fragment, so the peer's browser navigated to the origin root with an empty query and the `s` param never reached `ReceivePage` (the sender saw a well-formed link and QR code, and the handshake silently dead-ended). **Sub-path preservation (PR #123):** #120's origin-only base then regressed sub-path deployments — the app's routes are indeed only `/` and `/receive/`, but the static build is routinely served under a sub-path (an org GitHub Pages site like `https://<org>.github.io/zero-share/`, or a self-hosted build, both documented in the README's "Deployment" section) — and the bare origin dropped that location, so the link pointed at a nonexistent `/receive` at the deployment root (a 404). `appBaseFrom` preserves every directory above the base-root page, so a sub-path base survives into the generated link (`https://<org>.github.io/zero-share/receive?s=...`) while a domain-root deployment stays byte-identical to the origin-only output. Both call sites and both legacy defects (the query-only split, the bare `.origin` / bare `window.location.origin` bases) are pinned against the real helpers in `tests/offer-link-fragment.test.mjs`. The four query params above are the only ones ever emitted. [`repo://src/utils/path.ts#L1-L37`], [`repo://src/components/OfferPage.svelte#L81-L101`], [`repo://tests/offer-link-fragment.test.mjs`], [`repo://astro.config.mjs#L8-L13`]

- **`s`** — the `sdpEncode`d local offer SDP. Required; if absent the receive page bounces to the app's **offer page** — `receiveBounceTarget(window.location.href)` strips the `receive` route leaf from the current URL and takes the containing directory (the offer page's URL, with no query/fragment leakage, sub-path preserved — a bare-origin bounce would drop a sub-path deployment's peer off the app entirely, PR #123) — and then throws. [`repo://src/components/ReceivePage.svelte#L27-L40`], [`repo://src/utils/path.ts#L26-L37`]
- **`i`** — ICE server override (STUN, or a user-typed TURN/custom value). The sender emits `resolveIceServer(sendOptions.iceServer)` — omitted when equal to the default — and the receive page accepts it **only when it passes the shared `isSupportedIceServer` predicate** (built-in STUN allowlist **plus any well-formed `stun:`/`turn:` URL**); anything else falls back to `DEFAULT_SEND_OPTIONS.iceServer` with an error toast, so both peers always resolve to the same server and a shared link can never point the peer's WebRTC stack at a malformed or attacker-controlled value. [`repo://src/components/OfferPage.svelte#L75-L101`], [`repo://src/components/ReceivePage.svelte#L62-L77`]
- **`c`** — chunk size. Omitted when equal to the default 32 KB.
- **`p`** — base64 RSA public key (SPKI) of the offer peer, present only when encryption is on. The receive side does not trust the param blindly: the import is caught, and a malformed base64/SPKI value downgrades the session to plaintext with an error toast instead of rejecting or silently sending with an undefined key. [`repo://src/components/ReceivePage.svelte#L46-L59`]

ICE config comes from the shared `isSupportedIceServer` predicate in `src/configs.ts`, which accepts the built-in `STUN_SERVERS` list (Google/sipgate/nextcloud/myvoipapp/voipstunt; the nextcloud relay is `stuns:` because it is served over TLS) **plus any well-formed `stun:`/`stuns:`/`turn:`/`turns:` URL** the sender types into the custom field. The offer page resolves both its `RTCPeerConnection` `iceServers` and the link's `i` param through `resolveIceServer`, and the receive page validates `i` with the same predicate, so a custom/TURN server chosen on the sender is honored by the receiver — asymmetric ICE servers can no longer silently break NAT traversal or TURN relaying. A value the sender rejects gets a visible "Invalid ICE server, using default" toast instead of a silent fallback. [`repo://src/configs.ts#L3-L35`], [`repo://src/configs.ts#L47-L54`], [`repo://src/components/OfferPage.svelte#L75-L117`], [`repo://src/components/ReceivePage.svelte#L62-L77`], [`repo://tests/ice-server-consistency.test.mjs`]

**`c` validation (user-controllable input).** Because the link is shared and `c` is attacker-influenceable, the receive page does not trust it blindly: it `parseInt`s `c` and accepts it **only if it is in `CHUNK_SIZE_OPTIONS`** (8/16/32/64/128 KB); NaN, 0, negative, or any other value falls back to the 32 KB default. This single source of truth (`CHUNK_SIZE_OPTIONS`) is also what the sender options UI offers. [`repo://src/components/ReceivePage.svelte#L38-L43`], [`repo://src/configs.ts#L56-L58`]

## Answer-code wire format

The answer page produces `answerSDP = sdpEncode(localAnswerSdp) + '|' + publicKeyBase64`. The `|` delimiter is unambiguous because the encoded SDP character set excludes it. `publicKeyBase64` is empty when the receiver downgraded to plaintext (malformed `p` key) — that empty-key code is a **valid, intentional artifact**, not a corrupted one. The offer page's `acceptAnswer` parses with `parseAnswerCode`, which splits on the **last** `|` (safe even if a key portion ever contains one) and distinguishes a missing separator (truly malformed) from a well-formed code with an empty key: on the latter it follows the receiver into plaintext (`effectiveEncrypt = false`, info toast) instead of bailing on the empty key and dead-ending the handshake; on a missing separator or a damaged non-empty key it toasts "Invalid encryption key in answer code" and returns before `setRemoteDescription`. On success the SDP decode + `setRemoteDescription` runs inside its own `try/catch` (PR #45): the answer code is user-pasted or QR-scanned with no validation, and `sdpDecode` throwing on a damaged payload would otherwise escape as an unhandled rejection, so it toasts "Invalid answer code" instead. `acceptAnswer` also guards up front against a closed peer (PR #104): after the channel's death handler has closed the `RTCPeerConnection`, a re-pasted answer code or late QR scan would otherwise reach `setRemoteDescription` against a closed peer and surface a misleading "Invalid answer code" — so it checks `!connection || connection.connectionState === 'closed'` and toasts "Connection lost — generate a new offer to connect" instead of signaling the dead peer. The receive page likewise decodes the user-controllable `s` param and calls `setRemoteDescription` inside a `try/catch` that toasts "Invalid SDP in link" instead of crashing the page during load (PR #45). [`repo://src/components/ReceivePage.svelte#L160-L176`], [`repo://src/components/OfferPage.svelte#L389-L455`], [`repo://tests/dead-channel-peer-close.test.mjs`]

## ICE candidate wait + timeout fallback

Both sides wait for ICE candidates to drain before freezing the SDP, but cap the wait at `WAIT_ICE_CANDIDATES_TIMEOUT` (3 s). If candidates don't finish in time, a `setTimeout` builds the link/code from the current `localDescription` anyway and shows a toast — the connection still forms (possibly slower) rather than hanging. On the offer side the two build paths are raced safely: the RSA keypair is minted **once** at the top of `generateOfferLink` and a per-invocation `offerBuilt` flag is claimed synchronously by whichever path (candidate completion or timeout) builds first, so the link — and its `p` key — is built at most once per invocation; and the whole generation is wrapped in `try/catch`, so a synchronous `RTCPeerConnection`/`createDataChannel`/`createOffer`/`setLocalDescription` failure toasts "Could not generate the offer" and re-enables the button instead of leaving the "Generating Offer" spinner stuck with an unhandled rejection.

**Regeneration is generation-safe.** A stale 3 s timer is a real hazard: its closure holds the previous generation's `publicKeyBase64`, but its guard reads the script-scope `connection` — after a regeneration that is the _new_ peer, so without a token check the timer would build a link whose `p` key belongs to the old (re-minted, now discarded) keypair and silently break every subsequent encrypted transfer. `generateOfferLink` therefore, before minting: clears the tracked `iceCandidateTimer`, nulls the old data channel's handlers and closes it, closes the old `RTCPeerConnection` (guarded on `connectionState !== 'closed'`, since `close()` throws `InvalidStateError` on an already-settled peer), resets the settled peer crypto (`rsaPub = undefined`, `effectiveEncrypt` re-pinned from the live setting — so the new generation never encrypts with the previous peer's RSA key or the previous session's mode, PR #68) and the dead generation's UI state (new-file badge, `isConnecting`, pending answer code, **and the dead generation's `offerLink`** — its SDP belongs to the just-closed peer and its `p` key to the keypair about to be re-minted, so even a somehow-answered handshake would break encrypted transfers and `acceptAnswer()` would apply the answer to the new peer and reject every answer from a peer who opened the stale link; clearing it in the teardown — not only the catch — guarantees a failed regeneration returns to the clean "generate" state with no dead link to copy/QR/accept, and the template's `offerLink !== ''` gate re-locks/unlocks with the actual live link), and bumps a monotonically increasing `offerGeneration` counter; the timeout fallback re-checks its captured generation against the current one at fire time and bails if it is stale. **A failed generation is likewise torn down (PR #108):** the whole `createPeerAndDataCannel`/`createOffer`/`setLocalDescription` flow is wrapped in `try/catch`, and when it rejects the catch clears the just-started ICE-candidate timer, nulls the four handlers on the just-created data channel before `dataChannel.close()` (and resets it to `undefined`), and closes the just-created `RTCPeerConnection` guarded on `connectionState !== 'closed'` — otherwise the failed peer's ICE agent, UDP sockets, and STUN/TURN keepalives would leak until the next generation or page unload, the pending timer would keep a reference to the dead peer, and the channel's late-firing `onerror`/`onclose` handlers would stomp the current generation's `isConnecting`/`offerLink` (a stale answer-code paste would also run `setRemoteDescription` against the dead peer). When the failure happened before the peer/channel existed (e.g. `new RTCPeerConnection` threw), both guards skip and the still-closed previous generation is left untouched. The offer page therefore now has **four** guarded `connection.close()` call sites — the two channel-death handlers, the regeneration teardown, and the offer-creation catch — which `tests/dead-channel-peer-close.test.mjs` asserts. [`repo://src/components/OfferPage.svelte#L188-L268`], [`repo://src/components/OfferPage.svelte#L230-L244`], [`repo://src/components/OfferPage.svelte#L329-L360`], [`repo://src/components/ReceivePage.svelte#L176-L214`], [`repo://src/configs.ts#L68`], [`repo://tests/offer-peer-lifecycle.test.mjs`], [`repo://tests/regen-offer-stale-peer-crypto.test.mjs`], [`repo://tests/dead-channel-peer-close.test.mjs`]

## Data channel role swap

The **offer** side is the data-channel creator (`createDataChannel('data', { ordered: false })`); the **answer** side receives it via `ondatachannel`. **Binary frames are real bytes, not Blobs:** both pages pin `dataChannel.binaryType = 'arraybuffer'` immediately at channel acquisition — the offer side at the `createDataChannel` site, the answer side at the `ondatachannel` site — before the `onopen` wiring, because WebRTC's default `binaryType` is `'blob'`: with it every binary frame would arrive as a `Blob`, `new Uint8Array(blob)` in `handlePeerMessage` would yield a zero-length view, `Message.decode` would silently produce an empty message, and _every_ frame would be dropped — a guaranteed no-op transfer (PR #95). `tests/peer-message-handler.test.mjs` statically pins this: `binaryType = 'arraybuffer'` is set exactly once on each page at the acquisition site, before the `onopen` wiring. Both then install the same `handlePeerMessage` handler from `src/utils/peerMessage.ts` (deduplicated from two identical per-page handlers, PR #71), which dispatches the oneof payloads to `Receiver`/`Sender` with `Message.decode` on peer-controlled bytes guarded by `try/catch` (toast + drop the frame instead of an uncaught crash, PR #46). After `onopen`, the transfer UI (Send/Receive toggle) unlocks on both sides. Both pages additionally wire the channel's `onerror`/`onclose` to `sender?.onChannelClose()` / `receiver?.onChannelClose()` so a dead channel propagates the "connection lost" state into the file pipelines (PR #74); the `onChannelClose` bodies and the guarded `send()` they protect now live in the shared `src/utils/channelSender.ts` helper (PR #97). **Both `onerror` and `onclose` additionally call `connection.close()`** (PR #104), guarded on `connection.connectionState !== 'closed'`: closing the data channel alone does not close the `RTCPeerConnection` — its ICE agent, UDP sockets, and STUN/TURN keepalives would stay live for the rest of the page's lifetime (the same leak the regeneration teardown already handled for its dead peer). The guard is required because a double-fire (error-then-close) or a racing regeneration would otherwise throw `InvalidStateError` from `close()` on an already-settled peer. Pinned by `tests/dead-channel-peer-close.test.mjs` (static guard: each page's `dataChannel.onclose` **and** `onerror` handler contains a `connection.close()` call guarded on `connectionState !== 'closed'`, `OfferPage.acceptAnswer` bails before `setRemoteDescription` when the peer is missing or in the `closed` state, and the offer page carries **four** guarded `connection.close()` sites in total — the two channel-death handlers, the regeneration teardown, and the offer-creation catch added in PR #108). [`repo://src/components/OfferPage.svelte#L123-L185`], [`repo://src/components/ReceivePage.svelte#L99-L157`], [`repo://src/utils/peerMessage.ts`], [`repo://tests/peer-message-handler.test.mjs#L114-L172`], [`repo://tests/channel-sender.test.mjs`], [`repo://tests/dead-channel-peer-close.test.mjs`]

## QR exchange

`QrModal` renders any shareable artifact (offer link or answer code) as a QR code — byte mode via `new QRByte(data)` with no custom callback, so the library's built-in UTF-8 encoder (surrogate-pair aware) emits the matching ECI hint (`EncodingHint.UTF8` = 26), error-correction level M, auto version — via `buildQrDataUrl` in `src/utils/qr.ts`, and the data URL is **derived** (`$derived`) from the `qrData` prop so the QR always encodes the _current_ artifact: re-generating the offer (or any `qrData` change) re-renders the code instead of showing the stale mount-time copy (PR #53). The built-in encoder is deliberate: a bespoke byte/ECI callback previously truncated non-ASCII code points to their low UTF-16 byte and declared a wrong ECI (US-ASCII 27), corrupting any non-ASCII payload; PR #128 removed it so do not reintroduce one. `ScanQrModal` wraps `qr-scanner` to decode a counterparty's QR from the camera and feed it back as if pasted (offer page uses it to accept the answer; the receive page shows its answer QR). This makes link/code exchange camera-only, no keyboard. **Camera lifecycle is explicit:** a successful scan closes the modal programmatically (the checkbox `change` never fires), so `ScanQrModal` calls `stop()` on the scanner in the decode callback to release the camera stream + decode worker, and `onDestroy` repeats it if the component unmounts mid-scan; `stop()` is a no-op when already stopped. Both modals use per-instance DOM ids from a module-scope counter (safe because the pages mount Svelte `client:only` — no SSR), so multiple modals on one page never share toggles or video elements. [`repo://src/utils/qr.ts#L1-L23`], [`repo://src/components/qr/QrModal.svelte`], [`repo://src/components/qr/ScanQrModal.svelte`], [`repo://src/components/OfferPage.svelte#L425-L441`], [`repo://tests/qr.test.mjs`], [`repo://tests/scan-qr-lifecycle.test.mjs`]

## Failure behavior

- Missing/empty `s` on the receive page: bounce to the app's offer page via `receiveBounceTarget(window.location.href)` (the deployment base with the `receive` route leaf stripped — sub-path deployments stay inside the app, unlike the pre-#123 bare-origin bounce) + throw (no offer to answer). [`repo://src/components/ReceivePage.svelte#L27-L40`]
- **Malformed `s` on the receive page (PR #45):** the `s` param of a shared link is user-controllable; `sdpDecode` + `setRemoteDescription` in `setOfferSDP` run inside `try/catch`, so a crafted/truncated link toasts "Invalid SDP in link" instead of crashing the whole page during load. [`repo://src/components/ReceivePage.svelte#L138-L154`], [`repo://tests/sdp-robustness.test.mjs`]
- **Offer-processing failure dead-ends no longer (PR #49):** if the remote offer cannot be applied, `offerFailed` is set and the UI replaces the perpetual "Generating Answer" spinner with an error state ("Could not connect: the offer in the link is invalid / Ask the sender to generate a new offer link"); `generateAnswerSDP` awaits the offer-settling promise and checks `signalingState === 'have-remote-offer'` before `createAnswer`, and the whole generation is fire-and-forget with a `.catch` that surfaces any remaining rejection. [`repo://src/components/ReceivePage.svelte#L78-L83`], [`repo://src/components/ReceivePage.svelte#L168-L213`], [`repo://src/components/ReceivePage.svelte#L246-L256`], [`repo://tests/offer-processing-failure.test.mjs`]
- **Malformed answer code on the offer page (PR #45):** the pasted/scanned answer SDP is decoded inside `try/catch` in `acceptAnswer`; a damaged payload toasts "Invalid answer code" instead of an unhandled rejection with no visible error. [`repo://src/components/OfferPage.svelte#L331-L343`], [`repo://tests/sdp-robustness.test.mjs`]
- `onicecandidateerror`, `dataChannel.onerror`, `onclose`: toast an error, clear `isConnecting`, and (offer side) blank the offer link so a stale link isn't reused; both `onerror` and `onclose` additionally call `sender?.onChannelClose()` / `receiver?.onChannelClose()` so in-flight/queued files on both sides exit with an accurate "connection lost" error instead of dead-ending or re-firing false per-chunk errors (PR #74; the `onChannelClose` bodies and the guarded `send()` they protect now live in the shared `src/utils/channelSender.ts` helper, PR #97), and — since PR #104 — both `onerror` and `onclose` additionally call guarded `connection.close()` to release the `RTCPeerConnection` itself (closing the data channel alone leaves the ICE agent, UDP sockets, and STUN/TURN keepalives live; the guard prevents `InvalidStateError` from an error-then-close double-fire or a racing regeneration); offer-generation failures (synchronous constructor throws or rejected `createOffer`/`setLocalDescription`) toast "Could not generate the offer", re-enable the button, **and — since PR #108 — tear down the just-created generation with the same guarded shape as the regeneration teardown** (clear the pending ICE-candidate timer, null the four data-channel handlers before `dataChannel.close()`, and close the just-created `RTCPeerConnection` guarded on `connectionState !== 'closed'`), so a failed generation cannot leak its ICE agent/UDP sockets/STUN keepalives or let late-firing channel handlers stomp the current generation's UI. [`repo://src/components/OfferPage.svelte#L123-L185`], [`repo://src/components/OfferPage.svelte#L164-L295`], [`repo://src/components/ReceivePage.svelte#L119-L157`], [`repo://tests/dead-channel-peer-close.test.mjs`]
- Encryption off: `p`/public key are absent, `isEncrypt` derives false on the receive side, and peering is unencrypted end-to-end at this layer. A malformed `p` (or an `i` outside the shared predicate) is likewise downgraded/fallen-back-to-default — with a toast — so the session never advertises what it cannot honor. [`repo://src/components/ReceivePage.svelte#L34-L37`], [`repo://src/components/ReceivePage.svelte#L46-L77`]
- **Copy buttons never dead-end the manual handshake silently (PR #79).** The Copy Link (offer page) and Copy Answer (receive page) buttons are the keyboard-free path of the link/code exchange, and both handlers — `copyOfferLink` and `copyAnswerCode` — wrap `navigator.clipboard.writeText` in `try/catch`: a rejection (SecurityError in a non-secure context, NotAllowedError on denied permission, DataError, or `navigator.clipboard` being undefined in some webviews) toasts "Copy failed — select the … text and copy it manually" instead of escaping as an unhandled rejection with zero feedback, which would leave the user believing the link/answer code was copied when it was not and dead-end the manual P2P handshake. [`repo://src/components/OfferPage.svelte#L297-L307`], [`repo://src/components/ReceivePage.svelte#L164-L174`], [`repo://tests/clipboard-copy-robustness.test.mjs`]
